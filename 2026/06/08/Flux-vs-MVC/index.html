Flux_vs_MVC

前情提要：之前在前司工作的时候多数项目都是使用的MVC的WEB框架，后面领导自己在调研的时候说WebFlux在高并发场景下性能比较好，然后让部分项目使用WebFlux进行重构，但是重构又不调整响应式的数据库连接框架，涉及到的数据库查询等还是阻塞等待！！！😂

从传统 Spring MVC 到响应式 Spring WebFlux 的蜕变

作为一名 Java 开发者，从传统的命令式编程拓宽到响应式编程（Reactive Programming）是一个重要的技术分水岭。本篇总结将带你一站式理清两者的核心差异、底层原理以及核心概念。

一、 核心差异对比：原理篇

传统 Web 框架与响应式框架最根本的区别在于 线程模型（Threading Model） 和 I/O 处理方式 的不同。

1. 传统 Web (Spring MVC)

  • 核心架构： 基于 Servlet 规范，采用 Thread-per-Request（每个请求一个线程） 模型。
  • 工作原理： 服务器（Tomcat）内部维护一个线程池。当一个 HTTP 请求进来，会分配一个独立的平台线程去全程负责这个请求。
  • I/O 瓶颈： 当代码执行到查询数据库（JDBC）、调用第三方远程微服务或读取本地文件时，该线程会进入 阻塞（Blocking） 状态。此时线程不消耗 CPU，但会死死占用约 1MB 的栈内存。如果并发请求量超过线程池上限，后续请求就必须排队，服务器资源利用率极低。

2. 响应式 Web (Spring WebFlux)

  • 核心架构： 基于 Reactive Streams（响应式流）规范，默认运行在 Netty 服务器上。
  • 工作原理： 采用 Event-Loop（事件循环） 架构。它只需要极少数的固定线程（通常等于 CPU 核心数）。
  • 非阻塞 I/O： 当请求遇到 I/O 操作时，处理线程不会死等，而是将 I/O 回调事件注册给操作系统后，立即释放去接待下一个 HTTP 请求。当 I/O 数据准备就绪时，操作系统会通知事件循环，由另一个空闲线程来继续处理后续的业务。
  • 高吞吐保障： 支持 背压（Backpressure） 机制，允许下游消费者根据自己的处理能力反向限制上游生产者的发送速率，防止内存溢出（OOM）。

二、 编程模型对比：使用篇

1. 核心心智模型的转变

  • Spring MVC（命令式）：我是个快递员。我开车去仓库拿快递，如果仓库还没理好货，我就在门口死等（Block），拿到快递再送给客户。
  • Spring WebFlux（声明式/响应式）：我是个调度员。我接到订单后，画了一张快递配送路线图（Mono/Flux）丢给自动化机器人。机器人自己去跑，我立刻转头去接下一个订单。

2. 核心概念：Mono 与 Flux

在 WebFlux 中，你返回的不再是真实的数据对象，而是异步数据流的发射器（Publisher）。它们具有惰性求值（Lazy Evaluation）的特点：“Nothing Happens Until You Subscribe”（不订阅，什么都不会发生）。

核心组件 语义描述 集合类比 典型应用场景
Mono<T> 发射 0 或 1 个元素的异步序列 Optional<T> / CompletableFuture<T> 根据 ID 查询单个用户、执行没有返回值的删除操作（Mono<Void>）
Flux<T> 发射 0 到 N 个元素的异步连续序列 List<T> 的异步流动版 查询全部用户列表、实时消息推送、大文件分块流式传输

3. 数据管道中的三大信号

响应式流不靠返回值通信，而是靠沿管道传递的 信号（Signals）：

  1. onNext(T)：数据信号。每产生一个新元素就触发一次，Mono 最多触发 1 次，Flux 可触发多次。
  2. onComplete()：完成信号（终结符）。数据全部成功发完后触发，告诉下游可以收工了。
  3. onError(Throwable)：错误信号（终结符）。中途发生任何异常（如超时、报错）时触发，全线立刻停工。
  • 注意：在 WebFlux 中不能用传统 try-catch，需使用 .onErrorResume() 等响应式算子来拦截并降级错误信号。

三、 全景对比表

特性维度 Spring MVC (传统) Spring WebFlux (响应式)
默认内嵌服务器 Tomcat / Jetty Netty
并发执行模型 线程并发（依赖大量 OS 线程） 事件驱动（固定极少线程处理高并发）
控制层返回值 普通 Java 对象 / 集合 (User, List) 响应式流包裹对象 (Mono<User>, Flux<User>)
调用外部接口 RestTemplate (同步阻塞) WebClient (异步非阻塞)
数据库生态 JDBC 基于阻塞 (MyBatis, JPA/Hibernate) R2DBC 基于非阻塞 (或者 Reactive Mongo/Redis)
长连接天然支持 支持较弱，高并发下长连接容易跑满线程 极强，天然契合 SSE 与 WebSocket 的长连接推送

🚨 避坑第一铁律：

在 WebFlux 链路中，绝对不要手动调用 .block() 算子！
如果你在 WebFlux 中调用 .block() 强行同步获取数据，会直接锁死 Netty 极其宝贵的事件循环线程，导致整个服务器瞬间瘫痪！

四、 选型指南与现代思考（Java 21 时代）

1. 什么时候该选 Spring WebFlux？

  1. API 网关（Gateway）：不需要复杂业务，纯粹的高频 I/O 转发（如 Spring Cloud Gateway）。
  2. 高并发长连接系统：如大模型 AI 的打字机输出、实时聊天室、股票行情推送。WebFlux 可以用极低的系统资源维持数万个长连接。
  3. 全栈响应式环境：团队技术储备高，且底层数据库全部支持非阻塞驱动（R2DBC）。

2. 现代变局：虚拟线程（Project Loom）

在 Java 21+ 环境下，Spring Boot 支持了虚拟线程（Virtual Threads）：

启用后，Spring MVC 也可以在阻塞 I/O 时不跑满操作系统的物理线程。

💡 最终选型建议：

  • 针对 90% 的普通企业级 CRUD 微服务，优先选择 Spring MVC + 虚拟线程，既保留了命令式代码的简单好写、好调试，又兼顾了高并发。
  • 针对需要 真正的背压控制、高频全双工实时流（WebSocket/SSE）、或编写高性能网关 场景，Spring WebFlux 依然是无二的选择。

五、🛠 核心痛点：WebFlux 必须搭配哪些非阻塞生态？

要发挥 WebFlux 的真正威力，必须实现全链路非阻塞（Full Reactive Stack）。只要链路上有一个地方是阻塞的，非阻塞的链条就会断裂。

以下是 WebFlux 必须搭配的非阻塞组件：

  1. 数据库连接：必须抛弃 JDBC，拥抱 R2DBC
  • 传统 JDBC（如 Druid 线程池 + MyBatis / Hibernate）是强同步阻塞的，一个 SQL 没返回，线程就必须死等。
  • 必须使用 R2DBC (Reactive Relational Database Connectivity)。目前主流数据库（MySQL, PostgreSQL, Microsoft SQL Server）都有官方或社区提供的 R2DBC 响应式驱动。在 Spring 中对应的技术是 Spring Data R2DBC。
  1. NoSQL 缓存：使用 Reactive 版本
  • 不能再用传统的 Redis/Mongo 客户端。
  • 必须使用 Spring Data Reactive Redis（底层基于 Lettuce 的非阻塞模式）和 Spring Data Reactive MongoDB。
  1. 外部 HTTP 调用：抛弃 RestTemplate，改用 WebClient
  • RestTemplate 底层是阻塞的，调用第三方接口时会卡住线程。
  • 必须全量替换为 WebClient。

六、📋 避坑指南：从 MVC 重构成 WebFlux 的改造清单

如果你要将一个传统的 Spring MVC 项目真正、彻底地重构成 WebFlux，你需要做以下全方位的调整：

1. 依赖与服务器层的调整

  • 依赖调整：移除 spring-boot-starter-web，引入 spring-boot-starter-webflux。
  • 容器切换：底层内嵌容器会从 Tomcat 自动切换为 Netty。这意味着所有基于 Tomcat 的特定配置（如 server.tomcat.threads.max）全部失效，需要改为配置 Netty 相关的参数。

2. 数据库与持久层的重写（工作量最大）

  • 依赖替换：移除 mybatis-spring-boot-starter 或 spring-boot-starter-data-jpa，引入 spring-boot-starter-data-r2dbc。
  • 代码重写：
  • 所有的 Repository/Mapper 接口返回值必须从 User / List<User> 变为 Mono<User> / Flux<User>。
  • 彻底告别声明式事务 @Transactional 在传统多线程下的玩法（传统的事务是用 ThreadLocal 绑定连接的，而 WebFlux 的线程是跳跃的，必须改用 WebFlux 专用的响应式事务管理器 ReactiveTransactionManager）。

3. 控制层与业务层的代码范式转换

  • 接口签名：所有的 Controller 方法返回值全面改成 Mono<T> 或 Flux<T>。

  • 业务逻辑链式化：

  • 过去：A a = serviceA(); B b = serviceB(a); return b;

  • 改变后：必须全部改用 Reactor 操作符。return serviceA().flatMap(a -> serviceB(a));

  • 异常处理重构：传统的 @ExceptionHandler 虽然在 WebFlux 注解模式下还能用，但业务内部的 try-catch 块必须全部卸载，改用 .onErrorResume()、.onErrorReturn() 等流式防线。

4. 拦截器与安全认证的重写

  • 拦截器失效：传统的 Servlet HandlerInterceptor 和 Filter（基于 HttpServletRequest 和 HttpServletResponse）在 WebFlux 中完全无法运行。
  • 重写组件：
  • 拦截器需要重写为 WebFlux 的 WebFilter。
  • 操作的上下文对象变成了 ServerWebExchange。
  • 如果使用了安全框架，必须从 Spring Security 切换到 Spring Security Reactive。
