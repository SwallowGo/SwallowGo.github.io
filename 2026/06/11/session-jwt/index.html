🛠️ 从 Cookie 到双 Token：Web 登录状态管理演变史与 Java 落地实战

一、 演变脉络：四代登录状态管理的进化

发展阶段 技术方案 状态存储位置 核心痛点 适用场景
1. 早期阶段 纯 Cookie 记录 客户端浏览器 极其不安全，数据易被篡改 已被淘汰
2. 单体时代 原生 HttpSession 服务器内存 (Tomcat) 无法横向扩展（集群下无法共享） 小型单体项目
3. 分布式单体 Spring Session Redis 远程分布式缓存 (Redis) 依赖外部存储，有一定的内存开销 中大型单体、对状态强控要求高的系统
4. 前后端分离/微服务 无状态 Token (JWT / 双 Token) 客户端 (服务器无状态) 覆水难收（注销难、强控难） 现代微服务架构、跨端 App、SPA 应用

二、 单体架构标准：基于 Session 的状态管理

在传统的单体架构中，基于 Session 的状态管理是主流。Spring Web（Spring MVC）对底层的 Servlet API 进行了高级封装，使得开发人员能够以更优雅的方式来管理用户状态。

1. 底层实现原理

Tomcat 收到请求后，会解析 HTTP 请求头中的 Cookie，寻找名为 JSESSIONID 的值。

  • 如果找到，则匹配内存中的 HttpSession 对象。
  • 如果未找到，首次调用时会创建新 Session，并在响应头中自动添加 Set-Cookie: JSESSIONID=xxxxxx; Path=/; HttpOnly 返回给浏览器。

3. 集群痛点与 Spring Session Redis 的引入

单体 Session 最大的痛点是“服务重启或集群部署时状态丢失”。为了解决这个问题，通常会引入 Spring Session Redis。

它的引入极其简单，具备零侵入性：

  1. 加依赖：引入 spring-session-data-redis 和 spring-boot-starter-data-redis。
  2. 改配置：在 application.yml 中指定 spring.session.store-type: redis。
  3. 避坑指南：存入 Session 的对象必须实现 Serializable 接口；同时建议配置 GenericJackson2JsonRedisSerializer 替换默认的 JDK 序列化，防止 Redis 中出现二进制乱码。

三、 微服务时代：基于 JWT 的无状态认证

随着微服务架构的流行，为了追求完全的无状态（Stateless）和高扩展性，JWT（JSON Web Token） 逐渐取代了 Session。

1. JWT 的底层原理

JWT 是一个由小数点拼接的字符串：Header.Payload.Signature。

  • Header（头部）：声明令牌类型和签名算法（如 HS256）。
  • Payload（负载）：存放业务数据（如 userId、角色），它是可逆编码的，切记不要存放密码等敏感隐私信息。
  • Signature（签名）：防篡改的核心。利用服务器私钥对前两部分进行哈希加盐：

$$Signature = HMACSHA256(Base64(Header) + “.” + Base64(Payload), secretKey)$$

四、 完美折中：工业级双 Token 机制

尽管 JWT 很轻量，但它有一个致命缺陷：覆水难收（注销难）。Token 一旦发放出去，在到期前永远有效，服务器无法主动将其废弃。为了平衡“安全性”与“用户体验”，双 Token 机制应运而生。

1. 角色分工与无感刷新

双 Token 引入了两个令牌：

  • Access Token：用于业务鉴权。寿命极短（如 15 分钟），高频传输。
  • Refresh Token：用于续期。寿命较长（如 7 天），只在 Access Token 过期时，由前端（如 Axios 响应拦截器）在后台秘密调用续期接口，用它换取新的 Access Token。整个过程用户完全无感知。

2. 极致防线：Refresh Token 轮转与“自爆机制”

如果黑客连从未被使用过的 Refresh Token 也窃取了，并且抢在正牌用户之前进行了刷新，该怎么办？

业界通过 Refresh Token Rotation（轮转机制） 配合 Redis 构建了完美的自爆防线：

  1. 状态记录：虽然 JWT 是无状态的，但为了强控，后端会将 Refresh Token 记录在 Redis 中，并维护其状态（unused / used）。
  2. 黑客抢跑：黑客拿着偷来的 Refresh_A 请求续期。服务器发现其状态为 unused，予以放行，返回新 Access Token 和 **全新的 Refresh_B**。同时，将 Redis 中的 Refresh_A 标记为 used。
  3. 正牌触发自爆：几分钟后，正牌用户的 Access Token 过期，前端自动拿着手里的 Refresh_A 请求续期。
  4. 服务器断然惩罚：服务器一查，发现 Refresh_A 的状态居然是 used！服务器瞬间意识到遭遇了重放攻击（Token 被盗用）。
  5. 玉石俱焚：因为无法分辨谁是真用户，服务器立刻启动惩罚机制，清空该用户在 Redis 中的所有会话和有效 Token。
  6. 最终结局：黑客刚刚换取的 Refresh_B 瞬间沦为废纸，直接被踢下线。正牌用户虽然被迫重新登录（体验受损），但核心数据资产得到了切实的保护。

🎯 总结与技术选型建议

从有状态的分布式 Session，到无状态的 JWT，再到兼顾两者的双 Token 轮转自爆机制，Web 状态管理的演变本质上是在 安全、扩展性 与 用户体验 之间寻找最完美的平衡点。

  • 如果项目是中大型单体，且需要绝对的强控能力（如随时强制某人下线、封号）：首选 Spring Session Redis 方案，开发成本最低，且天然支持水平扩展。
  • 如果项目是纯粹的前后端分离、微服务架构，或者需要支持移动端多端接入：首选 双 Token 轮转方案（结合 Redis 做安全自爆），在保障微服务无状态、高性能的同时，将安全风险降到了最低。
