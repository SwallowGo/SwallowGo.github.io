🚀 Redis 核心技术与生产级运维学习总结

一、 为什么 Redis 这么快？

Redis 官方数据显示其读写性能可以达到 10 万+ QPS，这主要得益于以下四个核心设计：

  1. 纯内存操作 (Memory-Based)
  • 数据全部存储在内存中，CPU 读写内存的速度远超磁盘 I/O（纳秒级 vs 微秒/毫秒级）。
  1. 非阻塞的单线程模型 (Single-Threaded)
  • 核心的网络 I/O 和键值读写由单个主线程完成。
  • 优势：避免了频繁的 CPU 上下文切换开销，同时免去了多线程死锁、加锁及锁竞争的性能损耗。
  • 注：Redis 4.0+ 引入异步线程处理大 Key 删除；Redis 6.0+ 引入多线程处理网络 I/O，但核心命令执行仍为单线程。
  1. I/O 多路复用模型 (I/O Multiplexing)
  • 基于 Linux 的 epoll 机制，允许单个主线程同时监听成千上万个网络连接（Socket）。一旦有请求就绪，操作系统会通知 Redis 快速处理，实现高并发连接。
  1. 极致优化的底层数据结构
  • String：采用 SDS（简单动态字符串），获取长度时间复杂度为 $O(1)$，支持动态扩容。
  • Hash/List/Set/ZSet：内部根据数据量大小动态转换编码。例如 ZSet 在数据量大时使用 SkipList（跳表），保证 $O(\log N)$ 的高效查找。

二、 Redis 的定位与 5 大应用场景

1. 定位

Redis 是一个基于内存的、支持日志持久化的、高性能键值对（Key-Value）存储系统与内存数据库。

2. 经典使用场景

  • 🏎️ 高速缓存（Cache）：存储热点数据（商品详情、用户信息、Token 令牌），大幅减轻传统关系型数据库（如 MySQL）的读压力。
  • 🔒 分布式锁（Distributed Lock）：利用 SETNX 或 Redisson 组件，在微服务架构下确保全局业务互斥（如防止秒杀超卖）。
  • 📊 计数器与排行榜：利用 INCRBY 实现高并发点赞/库存扣减；利用 ZSet 实现实时热搜榜、积分排行榜。
  • ✉️ 轻量级消息队列：利用 List 的 LPUSH + BRPOP，或 Redis 5.0+ 的 Stream 结构（支持消费组和消息 ACK）实现异步解耦。
  • 🔑 会话保持（Session Store）：集中管理多台应用服务器的 Session 会话状态。

三、 Redis 四种部署架构及选型策略

1. 部署架构对比

部署方式 架构特点 优缺点 适合场景
单机模式 (Standalone) 单一实例负责全部读写。 部署最简单；但存在单点故障（SPOF），受单机内存限制。 开发测试环境、非核心内部工具。
主从复制 (Master-Slave) 主节点（Master）写，从节点（Slave）读，异步同步。 实现了读写分离，提升读并发；但不具备自动故障转移能力。 读多写少，能容忍一定人工恢复时间的场景。
哨兵模式 (Sentinel) 主从基础上引入哨兵集群，监控并自动故障转移。 高可用，自动选举新主并通知客户端；但写性能仍受单机 Master 限制。 数据量百 GB 以内，对高可用（HA）要求极高的核心业务。
切片集群 (Redis Cluster) 16384 个哈希槽分布式存储，去中心化。 横向扩展，解决单机内存和写性能瓶颈；但不支持跨节点批量操作。 海量数据（数百 GB 以上）或超高写并发的巨型互联网应用。

2. 选型三步决策法

  1. 环境维度：非生产环境/开发测试 $\rightarrow$ 优先选择 单机模式。
  2. 可用性维度：生产环境必须高可用 $\rightarrow$ 排除单机与纯主从，进入哨兵与集群的二选一。
  3. 容量与并发维度：
  • 数据量 $< 100\text{GB}$ 且写 QPS 较低 $\rightarrow$ 选择 哨兵模式（维护成本低，兼容性好）。
  • 数据量 $\ge$ 数百 GB 或写并发遭遇单机瓶颈 $\rightarrow$ 必须选择 切片集群模式 (Redis Cluster)。

四、 生产级故障应对预案

1. 单机/主从模式

  • 故障：进程崩溃或 Master 宕机导致无法写入。
  • 预案：
  • 使用 Systemd 或 Supervisor 配置进程挂掉自动拉起。
  • 必须开启 RDB+AOF，每天定时冷备 RDB 文件至异地。
  • 主从模式下需人工介入，对从节点执行 SLAVEOF NO ONE 升主，并修改其他从节点指向。业务层需配合限流/降级以防拖垮数据库。

2. 哨兵模式（自动自愈）

  • 流程：主观下线 $\rightarrow$ 客观下线 $\rightarrow$ 哨兵集群选举 Leader $\rightarrow$ 挑选最优 Slave 自动升主 $\rightarrow$ 通知客户端。

五、 生产环境扩容与平滑迁移方案

1. 扩容/迁移三种可行方案

  • 方案 A（集群内在线扩容）：Redis Cluster 架构下，通过 redis-cli --cluster add-node 加入新节点，再使用 reshard 命令在线迁移哈希槽。业务基于 ASK/MOVED 重定向机制，实现完全不停机。
  • 方案 B（跨架构平滑迁移）：单机/哨兵迁移到集群，或跨机房迁移。使用开源工具 RedisShake，配置 sync 模式。先通过 PSYNC 解析 RDB 进行全量同步，再持续监听 Oplog 进行增量同步。当延迟接近 0 毫秒时，业务端切换连接配置并重启，实现平滑割接。
  • 方案 C（紧急垂直扩容）：遭遇内存告警时的权宜之计。采用“滚轴式重启”：先调大 Slave 内存并重启 $\rightarrow$ 哨兵手动 Failover 提升 Slave 为新主 $\rightarrow$ 停机调大旧主内存 $\rightarrow$ 重启作为 Slave 重新加入。

2. 核心考虑点与避坑指南

  • ⚠️ 大 Key（BigKey）阻塞：迁移单个 Key 时底层是阻塞式的（DUMP + RESTORE）。迁移前必须使用 redis-cli --bigkeys 排查，严禁在高峰期迁移包含数万个元素的 BigKey，否则会导致主线程卡死。
  • 📈 复制缓冲区爆掉：如果源端写并发极高，全量同步时间长，会导致写命令覆盖掉 repl-backlog-buffer，从而引发无限循环全量同步。迁移前必须临时调大该缓冲区（如改至 512MB 或 1GB）。
  • 💻 客户端兼容性（Cluster 限制）：从单机/哨兵迁移到 Redis Cluster 后，代码中的批量操作（如 MGET/MSET/Pipeline）及 Lua 脚本中的所有 Key 必须位于同一个哈希槽（Slot）内，否则报错。必要时需在业务层引入 Hash Tag（如 {user:123}:info）进行重构。
  • 📊 内存安全线：显式设置 maxmemory。若开启 RDB 快照，Copy-On-Write 机制会消耗额外物理内存，建议 Redis 的 maxmemory 设置为机器物理内存的 70% ~ 80%。
