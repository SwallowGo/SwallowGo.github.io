Reactor 模型详解

什么是 Reactor 模型？

Reactor 模型（Reactor Pattern）是一种 事件驱动（Event Driven） 的高性能网络编程模型，主要用于处理高并发网络 I/O 请求。

它的核心思想是：

使用一个或多个线程监听所有 I/O 事件，当事件发生时，再将事件分发给对应的 Handler 进行处理，而不是为每一个连接创建一个线程。

整个模型充分利用了 I/O 多路复用（epoll、kqueue、IOCP 等），能够用极少量线程支撑数万甚至数十万连接。

为什么需要 Reactor 模型？

很多人容易误解：

Java NIO 不就是非阻塞了吗？为什么还需要 Reactor？

其实：

NIO 只是 Java 提供的一套 非阻塞 I/O API，它解决的是：

  • Socket 可以设置为非阻塞
  • 可以使用 Selector 管理多个 Channel

但是：

如何组织这些 Selector？
如何分发事件？
谁负责监听？
谁负责业务处理？

这些问题，NIO 都没有规定。

Reactor 就是一种 建立在 NIO 之上的设计模式。

另外还有一个误区：

很多资料说：

Reactor 比 NIO 更高效，因为 Reactor 使用 epoll，而 NIO 是轮询。

这个说法其实并不准确。

实际上：

Java NIO 的 Selector 在 Linux 下底层就是 epoll（JDK 1.6 以后）。

真正的区别是：

  • NIO 是 API
  • Reactor 是事件驱动架构

所以：

Reactor 并不是替代 NIO，而是利用 NIO 构建出高性能服务器架构。

Reactor 模型的特点

Reactor 主要具有以下几个特点：

  • 事件驱动

    • 所有 I/O 操作均由事件触发，而不是主动轮询。

  • 非阻塞

    • I/O 操作不会阻塞线程，线程始终可以处理其它连接。

  • 高资源利用率

    • 少量线程即可处理大量连接。

  • 职责分离

    • 将监听、事件分发、业务处理解耦，代码结构更加清晰。

Reactor 的三种实现模式

Reactor 一共有三种经典实现：

  1. 单线程 Reactor
  2. 多线程 Reactor
  3. 主从 Reactor（Master-Slave Reactor）

下面分别介绍。

一、单线程 Reactor

工作流程

  1. Reactor 持续监听所有客户端事件。
  2. 如果是连接事件：
    • Acceptor 执行 accept()
    • 注册到 Reactor
    • 创建对应 Handler
  3. 如果是读写事件：
    • Reactor 调用 Handler
    • Handler 完成：
      • Read
      • 业务处理
      • Send

整体流程：

优点

  • 架构简单
  • 无线程切换
  • 无锁竞争
  • 无线程同步问题

缺点

1. 无法利用多核 CPU

整个系统只有一个线程。

例如：

CPU 明明有 16 核，却只能使用 1 核。

2. Handler 阻塞整个 Reactor

如果业务执行较慢：

那么 Reactor 无法处理其它任何连接。

3. 单点故障

唯一线程如果：

  • 崩溃
  • 死循环
  • OOM

整个服务都会停止。

适用场景

适用于：

  • 客户端数量较少
  • 业务处理极快
  • Demo 或学习项目

二、多线程 Reactor


相比单线程 Reactor,最大的变化就是：

业务处理交给 Worker 线程池。

工作流程

  1. Reactor 监听所有事件。
  2. Acceptor 接收连接。
  3. Reactor 收到读事件。
  4. Handler 负责读取数据。
  5. 将业务提交给 Worker 线程池。
  6. Worker 完成业务。
  7. Handler 回写响应。

优点

能充分利用 CPU

例如：

多个业务可以同时执行。

Reactor 不会因为业务阻塞

因此吞吐量明显提高。

缺点

1. 多线程同步复杂

例如：

多个线程可能同时修改：

  • Session
  • Buffer
  • Channel 状态

需要：

  • synchronized
  • Lock
  • CAS

保证线程安全。

2. Reactor 仍可能成为瓶颈

虽然业务异步执行，

但是：

所有连接仍然由 一个 Reactor 监听。

例如：

当连接数量继续增加时：

Reactor 自己就成为瓶颈。

适用场景

适用于：

  • 中高并发
  • 业务处理耗时较短
  • CPU 密集型业务

三种 Reactor 模型对比

模型 优点 缺点 适用场景
单线程 Reactor 架构简单，无线程竞争 无法利用多核，业务阻塞整个 Reactor 客户端少、业务简单
多线程 Reactor 业务异步处理，可利用多核 CPU Reactor 仍是单点瓶颈，需要处理线程同步 中高并发、业务处理较轻
主从 Reactor 职责清晰，扩展性好，可支持超高并发 实现复杂，线程协调成本高 Netty、Nginx、RPC、高并发网关

Reactor 模型应用场景

Reactor 模型广泛应用于高性能网络框架：

  • Netty
  • Nginx
  • Redis
  • Kafka
  • ZooKeeper
  • Dubbo
  • RocketMQ

这些框架都采用了 Reactor 思想来实现高并发网络通信。

总结

Reactor 并不是一种具体技术，而是一种事件驱动设计模式。

它基于 I/O 多路复用（epoll、kqueue、IOCP），通过 事件监听 + 事件分发 + Handler 处理 的方式，实现了高性能、高并发的网络编程。

随着并发规模的提升，Reactor 的演进路线通常如下：

在实际生产环境中：

  • Netty 采用的是 主从 Reactor 多线程模型。
  • Nginx 采用的是 Master + Worker（多 Reactor）模型。
  • Redis 在网络层采用 Reactor 思想，并结合单线程事件循环实现高性能。
