设计模式

在软件开发中，大牛对软件系统的设计和开发总结了一些原则和模式，不管是用什么语言进行开发，都将对我们系统设计和开发提供指导意义。

设计模式分类

设计模式通常分为三大类：

创建型模式（Creational）：关注对象的创建过程，解耦对象的创建与使用（如：单例模式、工厂模式、抽象工厂模式、建造者模式、原型模式、生成器模式）。

结构型模式（Structural）：关注类或对象的组合，形成更大的结构（如：代理模式、适配器模式、装饰器模式、外观模式、享元模式等）。

行为型模式（Behavioral）：关注对象之间的通信、职责分配与算法实现（如：模板方法模式、策略模式、观察者模式、责任链模式、状态模式等）。

创建型模式

关注对象的创建过程，解耦对象的创建与使用。

单例模式

确保一个类只有一个实例，并提供该实例的全局访问点, 本文介绍6中常用的实现方式

类图

使用一个私有构造函数、一个私有静态变量以及一个公有静态函数来实现。

私有构造函数保证了不能通过构造函数来创建对象实例，只能通过公有静态函数返回唯一的私有静态变量。

实现方式

懒汉式-线程不安全

多线程下可能多次实例化

饿汉式-线程安全

类加载（Class Loading）时就完成单例对象的初始化。

缺点：丢失延迟实例化带来的节约资源的好处

懒汉式-线程安全

上锁的懒汉式，避免了多线程下可能多次实例化的问题，

缺点：会带来一定一定的性能损耗（锁竞争）

懒汉式-双重校验锁-线程安全

优化的线程安全版懒汉式，避免在已完成实例化情况下的锁竞争

通过延迟加载，通过同步锁 synchronized 和 volatile 保证线程安全与禁止指令重排序。支持懒加载，且只在第一次创建实例时进行加锁同步，后续调用性能好。

静态内部类实现

利用 JVM 的类加载机制来实现延迟加载和线程安全。外部类加载时，静态内部类不会被加载；只有第一次调用 getInstance() 触发内部类加载时，才会初始化单例实例。

缺点：传参困难，无法抗反射和抗序列化攻击

枚举实现

单例模式的最佳实践。

  • 抗反射：JDK 的 Constructor.newInstance() 源码中写死了检查：如果是枚举类型，直接抛出 IllegalArgumentException(“Cannot reflectively create enum objects”)
  • 抗序列化：Java 规范规定，枚举的序列化仅输出枚举常量的名称，反序列化时直接通过 Enum.valueOf() 寻找已存在的实例，绝不创建新对象。
在SpringBoot中的应用

Spring IoC容器：在Spring中，Bean默认的Scope就是singleton。这里Spring通过DdefaultSingletonBeanRegistry类来负责注册和缓存单例Bean，通过三级缓存(HashMap)来保证单例对象的唯一性和解决循环依赖。

工厂模式

将对象的创建过程封装起来，使客户端与具体类的实例化解耦。
具体实现可以分为简单工厂、工厂方法和抽象工厂。

实现方式

简单工厂

类图：简单工厂不是设计模式，更像是一种编程习惯。它把实例化的操作单独放到一个类中，这个类就成为简单工厂类，让简单工厂类来决定应该用哪个具体子类来实例化。

由一个静态方法根据传入的参数，动态决定创建并返回哪一个具体产品类的实例。适合创建产品类型较少且创建逻辑简单的场景。
缺点：违反开闭原则。

工厂方法

类图：定义一个创建对象的抽象接口（工厂接口），将具体的创建工作延迟到实现该接口的子类工厂中去完成。

缺点：类爆炸。每增加一个产品，旧需要成对增加具体产品和工厂类，增加了系统的抽象层级和复杂度。

在SpringBoot中的应用

在实际项目中，如果在客户端依然写 if (type == WECHAT) factory = new WeChatPayFactory()，客户端还是耦合了具体的工厂类。

在 Spring Boot 环境下，我们可以利用 Spring 的自动注入，将工厂方法模式写得极其优雅：策略模式 + 工厂方法注册表

抽象工厂

类图：提供一个接口，用于创建相关或依赖对象家族（产品族），而无需指定它们的具体类。这里使用了组合。

在SpringBoot中的应用

在 Spring / Spring Boot 框架中，抽象工厂模式（Abstract Factory Pattern） 的应用相比于工厂方法模式要更加隐蔽，但它在处理“产品族（一套相关联的对象）”以及跨平台/多组件集成时扮演着极其重要的角色。
案例一：ClientHttpRequestFactory（HTTP 客户端产品族工厂）
案例二：JpaVendorAdapter（JPA 持久层产品族适配工厂）
案例三：Embedded Servlet Container Factory（内嵌 Web 容器工厂）

对比

模式 抽象程度 核心目的 增加新产品时的做法 遵循开闭原则(OCP)
简单工厂 低 封装对象的创建过程 修改工厂类的 if-else ❌ 否
工厂方法 中 延迟对象创建到子类 新增产品类和对应的具体工厂类 ✅ 是

建造者模式

也叫生成器模式.
这里网络上众说纷纭。有的是说内部静态类实现创建，不提供setter，链式调用setter返回Builder本身，然后在build()方法做校验。关注怎么组装对象。

又有说是隐藏创建对象的建造过程 & 细节，使得用户在不知对象的建造过程 & 细节的情况下，就可直接创建复杂的对象。关注降低对象创建复杂度和隔离创建过程？

原型模式

使用原型实例指定要创建对象的类型，通过复制这个原型来创建新对象。

类图

只有在对象创建成本极高，或者需要保护原始对象状态的时候才需要。而且这里还设计深浅拷贝的问题！

实现方式

  1. 实现Java原生的Cloneable接口（默认浅拷贝）
  2. 使用序列化 / JSON 工具（推荐：天然实现深拷贝）
  3. 拷贝构造函数（Copy Constructor）

创建型小结

设计模式 核心一句话总结 适用场景 / 核心痛点
单例模式 (Singleton) 全局只有一个实例 线程池、配置中心、连接池等资源消耗大且需全局统一的对象
工厂方法模式 (Factory Method) 延迟到子类工厂去 new 对应产品 单一产品创建
抽象工厂模式 (Abstract Factory) 一次性生产一套相关联的“产品族” 跨平台/多组件库整体切换（如 Tomcat 切换为 Undertow、HttpClient 切换为 OkHttp）
建造者模式 (Builder) 分步/链式组装复杂的不可变对象 属性极多、有可选/必填校验、要求 final 线程安全的类
原型模式 (Prototype) 拿现有对象直接 clone 副本 对象创建成本极高（耗时/耗资源），或者需要深拷贝快照

结构型

关注类或对象的组合，形成更大的结构。

适配器模式

将一个类的接口, 转换成客户期望的另一个接口。 适配器让原本接口不兼容的类可以合作无间。 对象适配器使用组合, 类适配器使用多重继承。

对象适配器模式（组合）

类适配器模式（继承）不推荐

类适配器是通过让Adapter继承配适配者，然后实现目标接口

在SpringBoot中的应用

Spring 框架中广泛运用了适配器模式，最典型的莫过于 Spring MVC 的 HandlerAdapter。

在 Spring MVC 中，我们可以定义各种各样不同类型的 Controller（处理器 Handler）：

  • 实现 Controller 接口的类
  • 实现 HttpRequestHandler 接口的类
  • 用 @RequestMapping / @GetMapping 注解标记的方法（最常见）

Spring 的设计方案：引入 HandlerAdapter

  1. Spring引入了HandlerAdapter

  1. 各种具体的适配器类（各自适配对应的 Controller）

    • RequestMappingHandlerAdapter：专门负责适配处理加了 @RequestMapping 注解的方法。

    • SimpleControllerHandlerAdapter：专门负责适配实现了 org.springframework.web.servlet.mvc.Controller 接口的类。

    • HttpRequestHandlerAdapter：专门负责适配实现了 HttpRequestHandler 接口的类。

  2. DispatcherServlet 的优雅调用

    这里的逻辑并没有凭空减少，而是把集中式的、难以维护的控制逻辑（如巨型 if-else），分摊、解耦到了不同的独立组件中（通过多态、注册表等机制）。

装饰器模式

动态地将责任附加到对象上, 若要扩展功能, 装饰者提供了比继承更有弹性的替代方案，避免类继承爆炸。（从指数增长到线性增长）

实现方式

有四个核心角色：

  1. 抽象构件：定义被装饰的对象和装饰器的共同接口
  2. 具体构件：最原始的被装饰对象
  3. 抽象装饰器：实现抽象构件，并内部持有一个具体构件对象的引用
  4. 具体装饰器：具体的增强逻辑

代理模式

给目标对象提供一个代理对象，由代理对象控制对目标对象的访问。

实现方式

通常包含3个核心角色：

  1. 抽象主题：定义真实主题和代理对象的共同接口
  2. 真实主题，被代理的目标对象，包含真正的核心业务逻辑
  3. 代理：内部只有真实主题对象的引用，并且实现主题的接口，在调用真实业务逻辑前/后加入控制逻辑

在SpringBoot中的应用

在实际 Java 开发中，如果每个 Service 都去手写一个 XxxServiceProxy，就会产生大量的冗余代码（静态代理的弊端）。因此 Java/Spring 广泛使用了动态代理：

  1. JDK动态代理：基于接口生成代理类
  2. CGLIB动态代理，基于继承目标类的子类作为代理（不需要接口）

这也是Spring AOP的基石，事务管理、日志打印都基于代理模式实现。

结构型三剑客对比

这三个模式在 UML 类图和代码结构上极度相似——它们都在内部持有另一个对象的引用（Wrapper 结构）。很多开发者面试或者设计系统时非常容易混淆。

区分它们最关键的手段是看“设计的意图（Intent）”和“对客户端（Client）的视角”：

对比维度 适配器模式 (Adapter) 装饰器模式 (Decorator) 代理模式 (Proxy)
核心意图 接口转换解决接口不兼容问题，让旧代码在新系统复用。 动态功能增强/组合在不改变接口的前提下，动态叠加新功能（代替继承）。 控制访问与切面隔离在目标对象前后加控制逻辑（权限、日志、事务、延迟加载）。
接口是否改变 必须改变Adaptee 的接口被适配器包装成了全新的 Target 接口。 保持不变Decorator 和被装饰对象实现完全相同的 Component 接口。 保持不变Proxy 和被代理对象实现完全相同的 Subject 接口。
层叠/套娃能力 不强调多层嵌套（通常是一层接口转换）。 强强调多层套娃支持 A(B(C(target))) 递归叠加功能。 通常只有一层代理（客户端 ➔ 代理 ➔ 目标）。
目标对象的创建时机 通常由外部通过构造函数传入（组合对象）。 由外部显式创建并传入组合（如 new BufferedInputStream(new FileInputStream(…))）。 代理类可以自主创建/延迟加载真实对象（如虚拟代理/延迟加载）。
对客户端的透明度 客户端感知到了接口转换，显式调用新接口。 客户端知道自己在给对象“叠 Buff”。 完全透明客户端以为自己调用的就是真实对象（Spring 注入时无感知）。

文字总结：

  1. 适配器模式（Adapter）：”你原有的方法叫 payInUSD()，但我系统只认 payInRmb()，我帮你加个转换头。”（变接口，不改逻辑）

  2. 装饰器模式（Decorator）：”你的基础咖啡是 12 块，我给你套上一层牛奶装饰器加 3 块，再套上一层摩卡加 5 块。”（不变接口，叠功能/加属性）

  3. 代理模式（Proxy）：”你的业务方法叫 registerUser()，我实现一模一样的接口，但在你执行之前我检查权限，在之后我记录日志和开启事务。”（不变接口，控访问/切面处理）

关注对象之间的通信、职责分配与算法实现。

策略模式

定义一系列算法或业务逻辑，把它们一个个封装起来，并使它们可以相互替换。

说简单点就是 解决了 “行为/算法”的选择与切换的问题，在实际开发中就是消除硬编码if-else/switch-case的最强利器！

类图

为什么使用策略模式？

传统if-else/switch 违背开闭原则，如果使用场景会根据业务动态添加分支会容易出bug，并且方法体会极度膨胀。如果其他地方需要使用到某种特定逻辑也无法复用。

标准写法

核心角色：

  1. 抽象策略（Strategy）：定义策略的同一接口
  2. 具体策略（Concrete Strategy）：实现抽象策略，封装具体的算法逻辑
  3. 环境/上下文：持有策略的引用，供客户端使用

结合Spring的落地应用

在Spring中，结合依赖注入特性，我们可以优雅地实现策略的自动注册和动态路由：

  1. 抽象策略接口定义支持的类型标识
  2. 具体策略实现类注入为Spring Bean
  3. 策略工厂/服务层自动收集策略Map 效果：未来无论要增加多少种规则，现有的 DiscountService 代码一行都不用改！ 只需要新建一个实现类并加 @Component 注解，Spring 就会自动扫描并注册到 Map 中，完完全全遵循开闭原则（OCP）。

状态模式

允许对象在内部状态改变时改变它的行为，对象看起来好像修改了它所属的类。

类图

为什么使用状态模式？

当业务的一个具体对象存在多种状态，并且每种状态执行不同方式时需要判断状态类型时，使用if-else/switch导致状态和行为耦合，容易出现bug。

标准写法

状态模式包括3个核心角色

  1. 抽象状态
  2. 具体状态
  3. 上下文

基本上跟策略模式很像，但是这里主要的区别在业务流转过程中，Context 内部持有的状态对象在频繁动态改变。
