以上是最原始的生产方式，有另外几种更加简单的方式

  • 使用lambda表达式生产消息

    • public class LongEventMain
{
    public static void main(String[] args) throws Exception
    {
        int bufferSize = 1024; 

        Disruptor<LongEvent> disruptor = 
                new Disruptor<>(LongEvent::new, bufferSize, DaemonThreadFactory.INSTANCE);

        disruptor.handleEventsWith((event, sequence, endOfBatch) ->
                System.out.println("Event: " + event)); 
        disruptor.start(); 


        RingBuffer<LongEvent> ringBuffer = disruptor.getRingBuffer(); 
        ByteBuffer bb = ByteBuffer.allocate(8);
        for (long l = 0; true; l++)
        {
            bb.putLong(0, l);
            ringBuffer.publishEvent((event, sequence, buffer) -> event.set(buffer.getLong(0)), bb);
            Thread.sleep(1000);
        }
    }
}

  • 使用 Translators

    • public class LongEventProducer
{
    private final RingBuffer<LongEvent> ringBuffer;

    public LongEventProducer(RingBuffer<LongEvent> ringBuffer)
    {
        this.ringBuffer = ringBuffer;
    }

    private static final EventTranslatorOneArg<LongEvent, ByteBuffer> TRANSLATOR =
        new EventTranslatorOneArg<LongEvent, ByteBuffer>()
        {
            @Override
            public void translateTo(LongEvent event, long sequence, ByteBuffer bb)
            {
                event.set(bb.getLong(0));
            }
        };

    public void onData(ByteBuffer bb)
    {
        ringBuffer.publishEvent(TRANSLATOR, bb);
    }
}

调优

在Disruptor中，只有两个参数可以影响到性能，一个是生产者模式，一个是等待策略。

  • ProducerType.SINGLE vs Producer.MULTI
    • 官方测试下SINGLE模式下性能比MULTI好，所以如果对消费延迟有要求，最好使用SINGLE模式
  • 等待策略
    • BlockingWaitStrategy 默认的等待策略，使用经典的锁和条件变量去唤醒线程，CPU使用保守，慢
    • SleepingWaitStrategy 和BlockingWaitStrategy一样，CPU使用保守，但是没有使用锁，而是使用LockSupport.parkNanos(1).这个适用于对于延迟没有要求的场景，例如异步日志处理等。
    • YieldingWaitStrategy 是两个可以用在低延迟场景的等待策略之一，CPU使用效率高。如果处理线程比逻辑核要少，并且高性能的时候推荐使用。可以使用超线程。
    • BusySpinWaitStrategy 是性能最强的等待策略，通过自旋来不断充实，减少线程切换导致的系统调用从而减低延迟，推荐在线程板顶固定CPU下的场景，使用时处理线程要比物理核少并禁用超线程。
    • PhasedBackoffWaitStrategy 自旋+自定义策略，使用CPU资源紧张、吞吐量和延迟不重要的场景。

Disruptor简解

Disruptor官网文档：LMAX Disruptor User Guide

上图来源于官网手册

从上图中了解我们可以了解到Disruptor的一些概念。首先是生产者Producer，实际上Disruptor没有一个生产者的实体，如我们上文中的DisruptorMqServiceImpl通过RingBuffer获取对应序列号的消息对象MessageModel的引用将消息设置进去 就是一个生产的过程，这个方法可以自由被调用。此时基于等待策略等待就绪事件的对应的SequenceBarrier就会拿到这个消息的序列号并传递给消费者即EventHandler，EventHandler会基于当前收到的序列号到RingBuffer中获取对应的消息并处理。

Ring Buffer

顾名思义，这是一个环形的缓存区，是Disruptor的底层数据结构，这个从官网介绍说从3.0开始可以被用户手动替换，可以根据场景来替换底层存储数据结构，并非是Disruptor的核心。

Sequencer

Sequencer是Disruptor的真正的核心。此接口的两种实现（单生产者、多生产者）实现了生产者和消费者之间快速、正确传递数据的所有并发算法。消息的生产和消费者获取都是通过Sequencer来实现的。

其他的概念都不那么重要，可以去官网查阅。

Disruptor为什么快

  • 无锁设计

    「目前Java内置队列保证线程安全的方式：」

    ArrayBlockingQueue：基于数组形式的队列，通过加锁的方式，来保证多线程情况下数据的安全；

    LinkedBlockingQueue：基于链表形式的队列，也通过加锁的方式，来保证多线程情况下数据的安全；

    ConcurrentLinkedQueue：基于链表形式的队列，通过CAS的方式。

    而Disruptor的5中等待策略，只有**BlockingWaitStrategy**是通过上锁来保证数据线程安全的，其他的都是无锁的设计，减少了线程挂起切换的开销。

  • 环形数组结构

    • 空间换时间

      • 通过预先分配的空间复用，减少GC

    • 分支预测

      • 通过数组构成一个循环队列，它在初始化时就固定了存储空间，按照局部性原理，一次即可加载批量的元素到缓存行中，结合CPU的分支预测机制，因为数组的顺序加载规律分支预测器可以非常高效的预测并缓存下一条指令从而快速获取到数组中的下一个元素。

    • 缓存填充

      • 为了避免伪共享问题RingBufferFields继承RingBufferPad保证RingBufferFields每次被加载时前方都有7个8字节的数据填充。同理RingBuffer继承RingBufferFields在其后方填充7个8字节数据，由此保证了每一个RingBufferFields的任意字段被加载时，都有7个不可变的字段填充再任意CPU左右，避免RingBufferFields某个字段更新后，其他CPU缓存行的数据变为脏数据的缓存一致性问题(jdk1.8中有专门的注解@Contended来避免伪共享,更加优雅，不用手动填充)
